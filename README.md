# Кабинет Валентины и учеников

Русский язык и литература, подготовка к ЕГЭ. Статический интерфейс на GitHub Pages, авторизация, данные и файлы в Supabase. Сборка не нужна.

## Что умеет

- Преподаватель добавляет зарегистрированного ученика по почте и создаёт занятие нажатием на дату. Имя ученика отображается в графике.
- У занятия есть текст домашнего задания и раздел «На что обратить внимание». Преподаватель может добавлять и менять их после встречи.
- Вложения: JPG, PNG, WebP, PDF, TXT, DOC/DOCX, до 10 МБ каждое; до 10 выбранных файлов за одну загрузку. Файлы сохраняются отдельно от текста, сразу после нажатия «Загрузить выбранные файлы».
- Ученик видит свои занятия и материалы, читает задание и скачивает файлы. Он не меняет расписание или задания и не видит других учеников.
- Можно менять своё отображаемое имя, выходить, обновлять данные с другого устройства.
- Время московское (UTC+3). Наложение занятий запрещено сервером; параллельное изменение задания не затирает свежую версию.

## Включение кабинетов в существующем Supabase

1. В SQL Editor выполните **`supabase/portal.sql`**. Он создаёт профили, связи преподавателя с учениками, занятия и закрытое хранилище файлов. Повторное выполнение допустимо. Старую таблицу `schedules` и её данные он не меняет.
2. Аккаунт `g.nikulshin1201@gmail.com` должен быть зарегистрирован. Выполните **`supabase/teacher.sql`**: он назначает этому аккаунту роль преподавателя и имя «Валентина». Другие пользователи становятся учениками; регистрация не позволяет выбрать роль преподавателя.
3. Обновите сайт и войдите. Преподавателю доступны «+ Ученик» и «+ Занятие». Ученик сначала регистрируется, указывая имя и почту; затем преподаватель вводит его почту в «+ Ученик» и назначает урок.
4. Под двумя отдельными аккаунтами проверьте настоящее занятие, текст задания и тестовый файл. Во втором ученическом аккаунте они не должны отображаться. Локальная проверка PostgreSQL не заменяет эту проверку в вашем Supabase.

Позже измените почту **того же пользователя** в Supabase Authentication → Users. Связи хранятся по UUID, поэтому расписание и ученики сохранятся. Не удаляйте пользователя для смены почты. Если нужен совершенно другой существующий аккаунт преподавателя, перенос связей требует отдельной миграции.

### Существующее расписание

Пока новая схема не установлена, сайт продолжает показывать прежний личный планировщик. После установки преподаватель может открыть его кнопкой «Открыть прежнее расписание». Данные не удаляются и автоматически ученикам не назначаются. Новые уроки с учениками создаются в кабинете. Экспорт/импорт JSON относится только к прежнему планировщику и не включает новые занятия и файлы.

## Для нового проекта

- В SQL Editor сначала выполните `supabase/schema.sql`, затем шаги включения кабинетов выше.
- В Authentication → Sign In / Providers включите Email/Password и Allow new users to sign up. При включённом Confirm email нужно перейти по ссылке из письма и затем войти на сайте. Для отправки писем произвольным адресатам настройте свой SMTP: встроенная почта Supabase ограничена.
- Site URL и Redirect URLs: `https://gnikulshin1201-dot.github.io/-/`.
- В `config.js` хранятся только публичные Project URL и Publishable key. **Пароли, secret key и service_role в код и GitHub не добавляются.** Утёкший секретный ключ необходимо отозвать в Supabase.
- GitHub Settings → Pages → Source → GitHub Actions. Workflow публикует публичные файлы из main. SQL и тестовые данные в опубликованный сайт не входят.

## Доступ к данным

У таблиц включён Row Level Security. Учитель читает только связанных с ним учеников и свои занятия; ученик — собственный профиль и назначенные ему занятия. У пользователя есть право менять только своё имя, а не роль. Поиск ученика по точной почте разрешён только преподавателю через отдельную функцию базы.

Bucket `homework` закрытый. Преподаватель загружает/удаляет файлы своих занятий, ученик только читает вложения своих занятий. Ссылки скачивания действуют 60 секунд; тот, кто получил такую ссылку, может воспользоваться ею до истечения срока. Пароли не сохраняются в браузере; токены сеанса хранятся в sessionStorage вкладки. Это первая версия без сдачи работ учеником, уведомлений, оплаты и чата.

## Локальный запуск и проверки

```sh
python3 -m http.server 8000
```

Тест политик доступа на отдельной PostgreSQL 17 в Docker (изолированная сеть, без открытых портов, контейнер удаляется после проверки):

```sh
bash tests/run-db.sh
```

Проверяет миграцию и её повторное выполнение, права преподавателя/ученика/анонима, ограничения файлов и ролей, наложения занятий и версии. Управляемые auth/storage-таблицы Supabase представлены минимальными тестовыми аналогами; подписывание ссылок и загрузку настоящих файлов этот тест не проверяет.

Браузерный сценарий с Playwright и Chromium (API Supabase имитируется):

```sh
npm install --prefix /tmp/valentina-ui-tests --no-package-lock --no-save playwright
NODE_PATH=/tmp/valentina-ui-tests/node_modules node tests/portal-ui.cjs
```

При необходимости задайте `CHROMIUM_PATH` и `SITE_URL`. Проверяются преподаватель и ученик, создание занятия по дате, имена, экранирование текста, задание, вложение, скачивание, выход, ширины 1440/390/320. Эти проверки выполнены локально. Миграции и новые функции в действующем Supabase ещё не проверены: проект нужно обновить через SQL Editor.

## Восстановление пароля

На экране входа ученик вводит почту и нажимает «Забыли пароль?». Supabase отправляет письмо, после перехода по ссылке сайт открывает форму нового пароля. Ссылка проверяется сервером, токены сразу убираются из адресной строки. Новый пароль сохраняется для того же UUID: ученики, занятия и задания не теряются. После смены запрашивается завершение остальных сеансов, пользователь входит заново.

В Authentication → URL Configuration должны быть Site URL и разрешённый Redirect URL `https://gnikulshin1201-dot.github.io/-/`. Для доставки произвольным адресатам настройте SMTP и шаблон Reset Password с `{{ .ConfirmationURL }}`. Встроенная почта Supabase ограничена. Проверьте реальную доставку тестовому пользователю: в локальных тестах письма имитируются.

Преподаватель на сайте не видит и не назначает чужие пароли. Владелец проекта может открыть Authentication → Users, найти ученика по почте и отправить письмо восстановления через действие пользователя. Не удаляйте ученика и не создавайте аккаунт повторно для сброса пароля. Если утрачена сама почта, сначала проверьте личность ученика и помогите восстановить почтовый ящик; смена адреса аккаунта выполняется владельцем проекта отдельно.

Локальная проверка восстановления: `node tests/recovery-ui.cjs` (Playwright, запущенный HTTP-сервер, `SITE_URL`/`CHROMIUM_PATH` при необходимости). Проверяются запрос письма без раскрытия наличия аккаунта, восстановительный сеанс, удаление токенов из URL, перезагрузка, несовпадение паролей, смена пароля, выход и просроченная ссылка.
